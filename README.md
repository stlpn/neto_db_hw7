### Задание 1
#### активный master-сервер и пассивный репликационный slave-сервер

Преимущества данной конфигурации в том, что повышается отказоустойчивость за счет того, что пассивный сервер может взять роль основного, если он выйдет из строя, и отсутствуют проблемы с целостностью данных, за счет того, что чтение идет только с основного сервера. Так же может снять нагрузку с основного сервера за счет того, что slave-сервер может служить для снятия с него бекапов данных.
#### master-сервер и несколько slave-серверов

Основным преимуществом данной конфигурации является увеличение пропускной способности при чтении данных, за счет того, что читают с разных серверов, а основной только записывает данные, и нагрузка на основной сервер снижается. Так же можно разместить сервера в разных регионах, что может снизить задержки у конечных пользователей при чтении.

### Задание 2


Так как столбцы произвольно, то опишем их следующим образом:
- users (Пользователи): user_id, email, password, full_name, city, created_at.
- books (Книги): book_id, title, author, genre, price, description, cover_image_url.
- stores (Магазины): store_id, name, city, address, working_hours.

#### Вертикальный шардинг:
Разделим все таблицы на отдельные физические сервера. Таблицы users и books содержат много данных, для них нужны отдельные более мощные сервера. Так же для столбцы description и cover_image_url таблицы books вынесем на отдельный сервер, чтобы основная информацию по кникам находилась быстрее, а описание и картинка при дополнительном запросе. Назовем таблицу books_details, соединятся с основной она будет по book_id.
Таблица stores скорее всего не будет содержать много данных, но поместить ее на сервер с дополнительной информацией по книгам мы не можем, т.к. будем его шардировать горизонтально, так что отведем для него отдельный менее мощный сервер.

#### Горизонтальный шардинг:

Таблицу users разделим горизонально по ключу шардирования user_id, от 0 до 1000000 будет хранится на одном сервере, от 1000001 до 2000000 на другом и так далее.
Таблицы books и books_details разделим аналогично по ключу book_id либо по genre, но этот вариант мне кажется хуже, т.к. данные могут распологаться не равномерно.
